Claude Designで画面を設計し、Codexで既存コードへ実装する。企画、実機テスト、買い切り課金、App Store審査までを往復した開発記録です。

React Native / Expo TypeScript StoreKit Claude Design × Codex

最終更新: 2026年8月23日

スマホアプリを作るには、企画、画面設計、実装、実機確認、課金、ストア審査という、性質の異なる仕事をつなぐ必要があります。はじめてのタロットでは、そのすべてを一つのAIへ丸投げするのではなく、Claude Designで画面と体験を可視化し、Codexで既存コードへ実装し、iPhoneで確かめて再び設計へ戻す方法を取りました。

この記事では、会話から始まった小さな企画が、全78枚の辞典、複数の占い、端末内履歴、買い切りProを備えたiPhoneアプリになるまでを、プロダクト設計と実装ワークフローの両面から紹介します。

前提: 今回作ったもの

はじめてのタロットは、タロット全78枚の意味を学びながら、1枚引きからケルト十字まで段階的に占える日本語のiPhoneアプリです。

一言で表すと、次のようなアプリです。

カードの意味を調べる辞典と、カード同士のつながりまで読む占いを、静かに一つの端末で完結できるタロットアプリ。

最初の企画は大アルカナ22枚と1枚引き・4枚引きでした。その後、実機テストと内容レビューを繰り返し、現在は小アルカナを含む全78枚、複数スプレッド、履歴、内省メモ、買い切りProまで拡張しています。

技術スタックは、TypeScript / React Native / Expo SDK 54でアプリを実装し、EAS BuildでiOSアプリをビルド、TestFlightで実機配布する構成です。履歴や相談テーマはAsyncStorageでiPhone内に保存し、買い切りProだけをexpo-iap経由でAppleのStoreKitへ接続しています。鑑定は外部の生成AIやサーバーを呼び出さず、全78枚のデータとTypeScriptの合成ロジックだけで端末内生成します。AIを使うのは開発時であり、利用者が入力した相談内容をAIへ送るアプリではありません。

flowchart LR
  APP["React Native / Expo"] --> LOGIC["TypeScript鑑定ロジック"]
  APP --> LOCAL["AsyncStorage / 端末内履歴"]
  APP --> IAP["expo-iap / StoreKit"]
  APP --> EAS["EAS Build"]
  EAS --> TF["TestFlight"]
  TF --> STORE["App Store"]

この技術構成を選んだ理由

Swift / SwiftUIによるiOSネイティブ実装ではなくExpoを採用したのは、JavaScriptとTypeScriptの一つのコードベースで画面、占いロジック、Web確認まで進められ、AIとの反復開発がしやすいためです。初期公開はiPhoneに集中しますが、Android展開の余地も残せます。

一方で、すべてをWeb技術だけで済ませているわけではありません。App Storeの購入と復元はAppleの仕組みを使う必要があるため、そこだけはexpo-iapを通してネイティブ課金へ接続します。Expo Goでは画面を素早く確認し、実際の購入はネイティブコードを含むTestFlight版で確認する、という役割分担です。

また、バックエンド、会員データベース、外部AI APIを持たないことも意図した設計です。運用費を抑えられるだけでなく、相談内容を端末外へ送らないという、このアプリのプライバシー上の価値につながっています。

解決したい課題

既存のタロットアプリには、カードの意味が短すぎる、結果が抽象的で自分の状況へ結び付けにくい、逆位置が必要以上に否定的、複雑なスプレッドが正しい形で表示されない、といった使いづらさがあります。

このアプリでは、次の4点を中核価値にしています。

  1. 初心者は結論から読め、中級者は象徴やカード同士の関係まで掘り下げられる。
  2. 単語の羅列ではなく、質問、位置、正逆、カード全体の偏りを組み合わせて読む。
  3. 厳しいカードも「悪い未来の確定」ではなく、停滞・過剰・不足・内向化を整える手掛かりとして扱う。
  4. 相談内容や履歴を外部へ送らず、端末内で安心して使える。

対象ユーザー

  • タロットを初めて使い、カード名や基本の意味から学びたい人
  • 一通り意味を知っているが、複数枚のつながりを読むのが難しい人
  • 恋愛、仕事、お金、人間関係について、自分で考えるきっかけが欲しい人
  • 広告、ログイン、トラッキングのない静かな占いアプリを使いたい人

本アプリは未来や事実を断定するためのものではありません。占いを、自己理解、状況整理、次の行動を選ぶための補助線として扱います。

主な機能

無料で使える機能

  • タロット全78枚のカード辞典
  • 正位置・逆位置、象徴、物語、ブレインマップ、恋愛、仕事、金運、人間関係の解説
  • 端末ごとに一日固定される「今日の一枚」
  • 1枚引き
  • 過去・現在・未来・助言の4枚引き
  • Yes / No
  • あなた・相手・二人の関係を読む3枚の相性占い
  • 正式な十字と杖の配置で表示する10枚のケルト十字（無料では結論・主要3位置・行動提案）
  • 占い結果への気づきメモ
  • 結果の共有
  • 端末内履歴24件と、直近の逆位置傾向の振り返り

買い切りProで追加される機能

  • ケルト十字の10位置すべてと総合傾向をつなぐ詳細鑑定
  • 推進力・注意条件・判断基準から二つの選択肢を比較する「選択の天秤」
  • 各月に加え、転換点、前半から後半、四半期の焦点まで読む「一年の扉」
  • 端末内履歴の上限を24件から120件へ拡張
  • サブスクリプションではなく、一度購入すれば継続利用できる非消耗型課金

ケルト十字の詳細鑑定は、インストールごとに1件だけ無料で試せます。体験対象にした鑑定は履歴から再読できます。

商品IDはhajimete_tarot_pro_lifetimeです。価格表示はアプリへ固定せず、StoreKitから利用者の地域に合う表示価格を取得します。

情報設計

アプリの下部ナビゲーションは、Claude Designの画面レビューを受けて、横スクロールする7項目から固定4タブへ再編しました。機能名をすべて並べるのではなく、利用目的を入口にしています。

画面 役割
ホーム 今日の一枚、最新結果、主要機能への入口
占う 1枚引き、4枚引き、Yes / No、相性、ケルト十字、Proスプレッドを選ぶ
辞典 78枚の検索と詳細学習
履歴 過去の結果、メモ、傾向を振り返る

Proは独立タブにせず、対象スプレッドのロック表示やホームから自然に案内します。ホームもストア紹介文から始めるのではなく、今日の一枚 → 占ってみる → 最近の結果の順に変え、最初の一操作までを短くしました。

flowchart LR
  H["ホーム"] --> D["辞典で学ぶ"]
  H --> Q["質問を入力する"]
  Q --> S["スプレッドを選ぶ"]
  S --> R["カードを引く"]
  R --> I["要約と各位置を読む"]
  I --> A["今日の一歩を決める"]
  I --> M["気づきをメモする"]
  M --> L["履歴で振り返る"]

辞典と占いを別機能として分断せず、調べる → 引く → 読む → 記録する → 学び直すという循環にしていることが構造上の特徴です。

UXの5レイヤーで見る設計

Strategy: なぜ作るか

利用者のゴールは「未来を言い当ててもらうこと」だけではありません。カードを通して状況を整理し、自分が動かせる部分を見つけることです。

プロダクト側のゴールは、無料でも十分役立つ辞典と占いを提供し、もっと深く継続して使いたい人にだけ買い切りProを選んでもらうことです。

Scope: 何を提供するか

無料範囲だけでも結論と行動へ到達できることを守り、Proでは同じカードをさらに分析する層を追加します。ケルト十字は無料でも結論・主要3位置・行動提案まで読め、Proでは10位置すべての関係と総合傾向を開きます。加えて、専用比較を行う2スプレッドと履歴拡張を提供します。

会員登録、広告、解析SDK、通知、クラウド同期、実行時の生成AI通信は入れていません。機能を増やすより、鑑定文の一貫性、読みやすさ、プライバシーを優先しています。

Structure: どう流れるか

質問入力から結果までの基本構造は、すべての占いで共通です。

  1. 利用者がテーマを入力する。
  2. アプリが重複なしでカードを引き、各カードへ正位置または逆位置を割り当てる。
  3. スプレッド固有の位置へカードを配置する。
  4. 質問分野、位置、カード、正逆を組み合わせて各位置を読む。
  5. 複数枚の偏りと関係から全体像を合成する。
  6. 最後に、現実で試せる小さな行動へ落とし込む。
  7. 結果と任意のメモを端末内履歴へ保存する。

Skeleton: 画面上でどう配置するか

  • 最初に要約を置き、結論を探して長文をさまよわなくてよい構成にする。
  • 各位置には番号、役割、カード名、正逆を常に表示する。
  • 結果は「やさしく」で結論と主要な根拠を先に見せ、「くわしく」で残りの位置や全体傾向を段階的に開く。
  • 4枚引きは上段に助言、下段に過去・現在・未来を配置する。
  • ケルト十字は1〜6枚の十字と7〜10枚の杖を実際の展開形で表示する。
  • 長い鑑定は見出し単位に分け、主要位置を初期表示し、「ほかのN枚も読む」で詳細を開く。
  • 「今日の一歩」を独立したカードにし、鑑定を現実の行動へつなぐ。
  • 質問欄ではiPhoneのキーボード表示を考慮し、実行時にキーボードを閉じる。
  • 辞典は、かな・漢字・英語名・カード番号から探せる検索、章ジャンプ、ブレインマップを備え、長文でも目的の項目へ移動できるようにする。

Surface: どう感じてもらうか

濃い茶、生成り、金色を基調とした紙面調の画面に、Rider-Waite-Smith系のカード画像を組み合わせています。Claude Designで作った「やさしい紙面」の方向性をもとに、神秘性は残しつつ、怖さや過剰な装飾よりも「落ち着いて読めること」を優先しました。

正位置と逆位置は警告色で分けず、同じ中立色のラベルで表示します。逆位置や厳しい結果では、意味を薄めて楽観的にするのではなく、現状の課題と変更可能な行動をセットで示します。利用者を落ち込ませず、同時に根拠のない安心も与えないトーンを目指しています。

鑑定生成のワークフロー

このアプリは、利用時にGPTや外部AIへ質問を送って鑑定しているわけではありません。78枚の独自データと、スプレッド別のルールを端末上で組み合わせて文章を生成します。

flowchart TD
  Q["利用者の質問"] --> C["恋愛・仕事・金運・人間関係などを推定"]
  C --> D["78枚から重複なしで抽選"]
  D --> O["正位置・逆位置を決定"]
  O --> P["スプレッドの位置へ割り当て"]
  P --> T["質問分野 × 位置 × 正逆で個別解釈"]
  T --> X["スート・大アルカナ・逆位置・数字の重なりを分析"]
  X --> S["要約・具体的な読み筋・全体傾向を合成"]
  S --> A["今日の一歩と内省の問い"]
  A --> H["端末内履歴へ保存"]

1. 質問を文脈へ変換する

入力された質問から、恋愛、仕事、金運、人間関係などの分野を端末内で推定します。相性占いでは、片思い、交際中、復縁、夫婦、仕事関係などの関係段階も読み分けます。ケルト十字では、質問に期間が含まれる場合、その時間軸も解釈へ反映します。

2. カード単体を位置の意味へ翻訳する

同じカードでも、現在、障害、潜在意識、近い未来、相手側、二人の関係、最終結果では読み方が変わります。カードの一般的な意味をそのまま貼り付けず、「その位置で何を表すのか」というレンズを通します。

3. 正位置と逆位置を読み分ける

逆位置は一律に悪い意味へ変換しません。カードごとに次の4軸のどれが強いかを持たせています。

  • 停滞: 力はあるが動いていない
  • 過剰: 力が強く出すぎている
  • 不足: 必要な力が十分に使えていない
  • 内向化: 外の出来事より内面で働いている

これにより、「悪いカードだった」で終わらず、何を調整できるかまで示します。

4. 複数枚の関係を読む

全体鑑定では、個々のカード以外に次のシグナルを確認します。

  • ワンド、カップ、ソード、ペンタクルの偏り
  • 大アルカナの枚数
  • 正位置と逆位置の比率
  • 同じ数字やコートカードの重なり
  • 相性占いにおける温度、緊張、安定、明瞭さ、相互性
  • ケルト十字における現在から結果までの連続性

この段階が、単なる「カード説明の横並び」と、スプレッドとしての鑑定を分ける部分です。

5. 行動へ落とし込む

最後は「当たる・外れる」だけで閉じず、連絡頻度を確認する、期限を決める、条件を書き出す、休息を取るなど、利用者が現実で試せる一歩へつなげます。

辞典コンテンツの構成

全78枚の辞典は、短い基本意味と長い学習プロフィールを分離しています。占い結果では短文を使い、辞典では次の章を深く読めます。

  • 大切な3ポイント
  • 世界観・人物像
  • 絵柄の象徴
  • 他カードとの物語的関係
  • リーディング上達のコツ
  • ブレインマップ
  • 正位置の意味・性質・助言
  • 逆位置の意味・性質・助言
  • 成長テーマと内省の問い
  • 恋愛、仕事、金運、人間関係それぞれの正位置・逆位置

参考資料や解説サイトは、論点、象徴、読みの幅を確認するために使います。著作権のある文章や図版をコピーせず、アプリ内の文章は独自に編集します。カード画像は、Wikimedia Commonsで公開されているRider-Waite-Smith系のパブリックドメイン画像を使用しています。

App.tsxが画面、タブ、入力、結果表示を担当し、鑑定ロジックはsrc/lib/readings.ts、全体傾向はsrc/lib/spreadSynthesis.ts、辞典はsrc/data配下へ分離しています。画面を直すときに鑑定ロジックを不用意に変えないよう、見た目、文章生成、保存、課金の境界を分けています。

図の大きな境界は、独自サーバーを持たず、辞典、鑑定、履歴、学習記録をiPhone内で完結させていることです。外部通信が必要なのは、買い切りProの購入と復元をexpo-iapからApple StoreKitへ問い合わせる経路だけです。

Claude Design × Codexの開発ワークフロー

このプロジェクトでは、AIへ一度だけ「アプリを作って」と依頼したのではありません。Claude Designをデザインレビューと画面設計に、Codexをコードベースの調査と実装に使い、最後は必ずiPhoneへ戻す反復を続けました。

  O["要望と実機での違和感"] --> CD["Claude Design / 画面案とレビュー"]
  CD --> H["優先度・数値・受け入れ条件を含む指示書"]
  H --> C["Codex / 既存コードへ実装"]
  C --> V["型検査・書き出し・リリース検査"]
  V --> I["Expo Go / TestFlightでiPhone確認"]
  I --> R["画面収録とスクリーンショット"]
  R --> CD
  I --> S["App Store提出素材へ反映"]

段階1: 企画とコンテンツを言葉で固める

対象ユーザー、カード範囲、必要な辞典項目、4枚引きの位置、無料版の範囲を会話で決めました。最初から全78枚や課金を前提にせず、まず「辞典で調べる」「1枚で読む」「4枚で流れを読む」という核を明文化しました。

カード単体の意味だけでなく、正逆、質問分野、スプレッド上の位置、複数枚の関係をデータとルールへ落としました。Claude / Claude Codeによる長文コンテンツの再構成も取り込み、Codexで型や参照関係、画面上の表示、占いロジックとの整合性を確認しています。

段階2: Codexで動くアプリへ変える

Codexは、会話で決めた仕様を現在のリポジトリへ直接反映します。既存ファイルと未保存の変更を調べ、データ型、鑑定ロジック、画面、端末内保存をつなぎ、型検査と書き出しまで実行します。

この段階で大切だったのは、文章だけを増やすのではなく、同じカードでも質問と位置によって読み方が変わる構造を作ることでした。ケルト十字もカードを横一列に並べるのではなく、十字と杖の配置を画面幅の中で成立させています。

段階3: Claude Designで実画面を設計し直す

機能が揃ったあと、App Store用スクリーンショットと約5分のiPhone画面収録をClaude Designへ渡しました。静止画では情報の階層と見た目を、動画ではスクロール量、キーボード、カードを引いた後の移動、購入状態など、操作して初めて分かる問題を確認しました。

レビュー結果は感想だけでなく、次のような実装可能な指示書にしました。

  • P0 / P1 / P2で優先順位を分ける。
  • 濃茶、生成り、金、赤茶など既存のデザイントークンを明記する。
  • 文字サイズ、余白、タップ領域、カード幅を数値で示す。
  • 変更してよい画面と、維持する鑑定ロジックを分ける。
  • iPhoneの各サイズで確認できる受け入れ条件を書く。

ここから、固定ヘッダーと二重スクロール、横スクロールする7タブ、長文が同じ強さで続く結果画面、小さすぎるケルト十字、かなや番号で見つからない辞典検索、購入済み状態や地域別価格の表示といった課題が、具体的な改修項目になりました。

段階4: Codexでデザインを既存コードへ移植する

Codexは指示書をそのまま上書きするのではなく、現在のReact Native実装と照合してから変更します。今回の改修では、主に次を反映しました。

  • 下部ナビゲーションをホーム / 占う / 辞典 / 履歴の固定4タブにする。
  • ホームの先頭を「今日の一枚」にし、占いまでの距離を短くする。
  • 結果を要約 → 主要な根拠 → 今日の一歩の順にし、詳細は段階的に開く。
  • 「やさしく / くわしく」で読む深さを選べるようにする。
  • 正位置と逆位置を同じ中立色で示し、逆位置の4軸を補助情報として扱う。
  • 辞典検索を、かな、漢字、英語名、番号、スート名へ対応させる。
  • Proの無料体験と詳細鑑定の境界を明確にし、StoreKitの地域別価格を表示する。

見た目の改修中も、readings.tsなどの鑑定ロジックを守る範囲を決めました。デザインの改善が占い結果を意図せず変えないようにするためです。

段階5: iPhoneで確かめ、設計へ戻す

Expo Goは画面や文章の素早い確認に、TestFlightはネイティブ課金と本番に近い動作確認に使い分けました。画像の品質、文章の途中切れ、質問入力中のキーボード、ケルト十字の配置、鑑定の具体性、否定的に感じる表現、購入と復元を実機で確認しています。

修正後も画面収録を取り直し、気になる場面を時系列のスクリーンショットにしてClaude Designへ戻しました。デザイン → コード → 実機 → デザインの輪を閉じることで、モックだけ美しく、実際には読みにくい状態を避けています。

段階6: App Store公開を実装の一部として扱う

型検査、Expo診断、iOS/Web書き出しに加え、画像の権利とクレジット、プライバシーポリシー、サポートページ、個人データを含まないストア画像、買い切りPro、購入復元、EAS本番ビルド、TestFlight、App Store Connectの審査情報まで整えました。

審査で説明が必要になったときも、実機動画、再現手順、修正版ビルド、審査メモを同じワークフローで更新します。「コードが動いたら完成」ではなく、利用者がストアから入手できるところまでをプロダクト開発に含めました。

役割分担

担当 主な役割
プロダクトオーナー 目標、利用者視点、占い品質の基準、実機での違和感を提示する
Claude Design 画面案、情報の優先順位、実機動画レビュー、数値と受け入れ条件を含む実装指示を作る
Claude / Claude Code 辞典など大量コンテンツの再構成と文章レビューを補助する
Codex コードベースを調査し、設計を実装し、レビュー、修正、検証、課金・公開準備を一貫して進める
Expo / EAS 開発サーバー、iOSビルド、提出を支える
Apple StoreKit、TestFlight、App Store審査と配布を担う

AIの役割を固定しすぎず、得意な粒度で使い分ける一方、最終的な品質基準は実際にアプリを使う人間側が持ちます。特に占い文は、文法的に正しいだけでは十分ではなく、具体性、温度、納得感、読み終えた後の感情まで実機で確認します。

基本確認コマンドは次の通りです。

npm run typecheck
npm run release:check
npx expo-doctor
npx expo export --platform web

画面内容はExpo Goで確認できます。ただし、実際のPro購入、購入完了、購入復元はネイティブのStoreKitが必要なため、TestFlightまたは開発ビルドで確認します。

出力品質を数値で確認する

きっかけは、Pro版のスプレッドを使っても「課金する価値がどこにあるのか分かりにくい」と感じたことでした。印象だけで直すのではなく、まず中身を疑って同じ条件で大量生成したところ、曖昧な結論が57.0%を占めることが分かり、ロジックを作り直してからもう一度測りました。

占い文は、数件を目で読んだだけでは偏りを見抜けません。そこでProスプレッドを数万回生成し、「同じ曖昧な結論に寄りすぎていないか」「転換点が特定の月へ固定されていないか」を集計しました。これは占いの的中率を測るものではなく、壊れている状態を数値で特定し、直り具合を同じ条件で確かめるテストです。

検査対象 改修前 改修後の再測定
選択の天秤が「差はありません」で終わる割合 57.0% 0.0%（30,000回）
一年の扉の転換点 6か月目に100%固定 2〜12か月目へ分散、最大9.9%（10,000回）

選択の天秤では、総合点が拮抗する場合もあります。ただし改修後は、推進力、注意条件、判断基準、カードの性質のどこに違いがあるかを必ず示すため、「結局同じ」という結論では終わりません。

一年の扉では、転換点をカード間のスート、正逆、大アルカナ、数字の変化から選ぶようにしました。再測定した10,000回では、各候補月の出現率は8.3〜9.9%でした。

大量生成は、目視では気づきにくい実バグの発見にも役立ちました。転換点が12か月目になると転換カードと最終カードが同一になり、同じ月とカードを二度読み上げる問題が約1割で起きていました。最終月だけ文型を分ける修正後は、10,000回のうち12か月目が転換点になった969件すべてで重複が0件になりました。同時に、「2026年8月の月から始まり」のような月名とカード名の重なりも、「2026年8月は月のカードから始まり」へ直しています。

このように、違和感を仕様へ変えるだけでなく、壊れている状態を数値で特定し、修正後に同じ条件で測り直すところまでを品質確認に含めています。

プライバシーと安全性の前提

  • 会員登録、氏名、メールアドレス、位置情報、連絡先を取得しない。
  • 相談テーマ、占い結果、内省メモは端末内だけに保存する。
  • 広告、アクセス解析、トラッキングを初期リリースへ入れない。
  • 実行時に質問をGPTや運営者のサーバーへ送信しない。
  • 利用者がOSの共有先を確定した場合だけ、選択した相手へ結果が渡る。
  • 履歴はアプリ内で削除でき、アプリを削除した場合も端末から消える。
  • 医療、法律、投資など重要な判断を占いだけで決めないよう明示する。

まとめ

はじめてのタロットの開発で重要だったのは、AIに一度で完成品を作らせることではなく、次の順番を守ったことです。

  1. 誰のどんな困りごとを解決するかを言葉で決める。
  2. 必要な機能とコンテンツの範囲を決める。
  3. 辞典、質問、カード、スプレッド、結果の関係を構造化する。
  4. 実機で使い、文章と操作の違和感を仕様へ戻す。
  5. 権利、プライバシー、課金、審査まで含めて公開品質へ整える。

AIは企画、文章、実装、レビュー、公開準備を高速化できます。しかし、利用者が結果を読んだときに「自分の状況を整理できた」「次に何をすればよいか分かった」と感じるかどうかは、実際の利用体験を何度も見直すことでしか磨けません。

Claude Designは、動いている画面を「どう見え、どう感じ、どこで迷うか」という設計へ戻してくれました。Codexは、その設計を既存コードの制約とつなぎ、動作確認とストア提出まで進めました。そして人間は、iPhoneを手にして違和感を言葉にし、どこまでを製品品質とするかを決めました。この三者の反復が、アプリを公開できる形へ育てる中心ワークフローです。
